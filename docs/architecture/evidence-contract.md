# Portfolio evidence v1: strict technical verification contract

**Lifecycle:** In Development / offline CI; signed publication and human governance are separate phases.  
**Date:** 2026-11-04.  
**Target:** New engineering evidence bundles only.  
**Legacy behavior:** `evidence/shared/validate_evidence.py` remains the compatibility validator; historical bundles are never rewritten.

## Why

A test badge alone cannot show which commit, dependencies, configuration,
test command, failure controls and result were actually checked. This
contract binds a machine-readable manifest to an exact candidate, tested
commit, base commit (for pull-request synthetic merges), workflow run ID and
attempt, recorded commands, measured tests and artifact digests.

A SHA-256 hash detects content changes. **It cannot authenticate execution.**
An agent could fabricate an internally consistent report. Trusted GitHub
workflow identity, independent review and a signed attestation are separate
requirements before presenting the result as independently verifiable.

## Contract

The canonical JSON Schema document is
`schemas/portfolio-evidence-v1.schema.json`. A stdlib-only verifier enforces
the required object shape, nested field allowlists, digest integrity,
report presence, nonempty suites, negative controls, explicit failure
reasons, timestamp order, retention bounds and exact run identity.

Mandatory distinctions:

- `candidateSha` — the PR head (or direct push SHA).
- `baseSha` — first parent of the GitHub PR synthetic merge; `null` for direct push.
- `testedSha` — commit actually checked out and executed in CI.
- `producer.sourceSha` — tested commit containing the evidence emitter.
- `environment.sourceTreeDigest` — SHA-256 of `git ls-tree -r --full-tree -z testedSha` bytes.
- `environment.configurationFiles`, `configurationDigest` and `lockfiles` —
  independently inspectable digests of named files.
- `verification.checks` — command identifiers, exit codes, test counts,
  a report artifact and negative-control outcomes, not a textual assertion of PASS.
- `artifacts` — relative paths, SHA-256 and byte length for every named proof.
- `approvalEffective` — strictly `false`. Human approval is never granted by
  candidate-authored JSON.

A passing strict verification cannot imply an accepted risk exception or
production deployment.

## Reproduce the code-level rejection contract

```sh
python3 scripts/ci/tests/test_portfolio_evidence.py -v
```

The tests include ten intentionally invalid bundles:

1. post-hash artifact tampering;
2. candidate SHA substitution;
3. missing test report;
4. duplicate JSON keys;
5. directory traversal;
6. symlink traversal outside the bundle;
7. a zero-test success claim;
8. the wrong negative-test failure reason;
9. NOT_EXECUTED incorrectly labeled PASS;
10. forged human approval.

Further negative cases cover unknown properties, duplicate artifacts,
unplanned skipped tests, incorrect rerun identity and swapped merge parents.

The authenticated workflow `.github/workflows/engineering-evidence.yml`
executes the narrow real unit-test suite, writes its captured command output
and report, emits structured evidence, validates it against GitHub execution
identity, and uploads artifacts, including diagnostics when possible. If any
required stage fails, the job remains failed. No required step uses
`continue-on-error`.

## Schema and verifier relationship

This initial implementation validates the JSON Schema document's syntax
and enforces its required fields using an explicit stdlib verifier. The
verifier is not a general JSON Schema Draft 2020-12 implementation.
Later hardening should add a pinned full-schema validator and differential
tests proving that schema acceptance and strict runtime validation agree.
Do not claim full standards-compliant JSON Schema validation until then.

## Existing integration gate and governance

The current integration gate's trusted manifest pins `scripts/ci/**`.
Adding these new verifier files changes the pinned surface. The historical
`merge-eligibility` failure is expected to remain fail-closed until a
reviewed trusted manifest update and the required human decisions exist.
This PR does **not** adjust the pin, invent review records, change the
owner allowlist or mark acceptance conditions MET.

A separately reportable **technical evidence** verdict is not a substitute
for acceptance or production readiness.

## Limitations and planned follow-up

- The v1 emitter consumes an observed JSON report generated by an actual
  workflow; it does not itself authenticate that report beyond its run
  identity and content. Signed provenance is a separate PR.
- Public GitHub Actions artifacts are retained for seven days by this
  workflow; they are **not** immutable or permanent. External WORM/Object
  Lock archival needs separate authorization and infrastructure.
- Tests of the new strict validator demonstrate rejection semantics,
  not live AWS/Entra/PostgreSQL operations.
- The existing legacy validator remains available; no historical evidence
  is retroactively upgraded or modified.
- A formal security review should inspect JSON path canonicalization, Git
  source identity, result-report provenance and untrusted PR execution
  before signing any published artifact.
- Dependency-lockfile coverage is explicit: the stdlib Python negative-test
  suite has no third-party Python lockfile. Other modules must declare their
  actual lockfile set; an empty map is not a claim of reproducible external
  dependencies.

## Further acceptance

A trusted main-branch publication workflow will eventually verify exact
identity, digest and permission scope and attach a GitHub artifact attestation
using a pinned action, but only **after** the technical result is validated.
This is not owner acceptance or an independently audited software release.

**Current label:** `EXECUTED_CI` only for runs with real workflow evidence;
`GOVERNANCE_PENDING`; `PRODUCTION_NOT_TESTED`.
